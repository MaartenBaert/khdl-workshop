[[reed-solomon-syndromes]]
=== RsSyndromes

Source: `rtl/reedsolo_syndromes.kh`.

==== Function and interfaces

`RsSyndromes` accepts a received systematic codeword, forwards its message
beats, and evaluates `R` syndromes using parallel full-width Horner updates.
With `P_n=(n +/ U)*U-n`, the evaluated polynomial is
`F(x)=x**P_n*C_received(x)`. Therefore
`S[j]=C_received(alpha**(fcr+j))*alpha**(P_n*(fcr+j))`. Zero padding does
not change whether a valid RS codeword has zero syndromes. `RsChien` must use
matching padded coordinates; see <<reed-solomon-positions>>.

`input` is `RsStream(U, decoded=false, RS=RS).Sink` with `C=(n +/ U)` beats per
codeword. `output` is `RsTransaction(RsSyndromesBlock(RS=RS)).Source`, carrying
the `R` syndromes. The first `K=(k +/ U)` codeword beats, which hold the
message, leave unchanged on the `message` stream, with `message_commit` and
`message_cancel` flags for a packet FIFO; see <<reed-solomon-message-path>>.
The stage clears known low-lane padding before arithmetic on the expected
final beat.

[cols="1,1,3",options="header"]
|===
|Parameter |Default |Effect / constraint
|RS |RsDefault |Code and field configuration.
|unroll |1 |Any positive input width `U`; also determines syndrome padding offset.
|buffered |false |Optional one-beat external input holding storage.
|===

==== Timing and malformed frames

With no holding beat pending and output space available, an accepted beat
updates the syndrome state at that edge. A correctly sized final beat
sets registered output `valid`, so the block can transfer on the next edge.
An isolated continuously supplied frame accepted from edge zero therefore
has its first possible output block transfer at edge `C`. With continuous
traffic and an always-ready consumer, successive frames take C cycles each.

.The complete syndrome transaction becomes available one edge after the fourth input transfer.
[wavedrom]
....
{"signal":[
  {"name":"clk","wave":"p....."},
  {"name":"input.valid","wave":"1...0."},
  {"name":"input.ready","wave":"1....."},
  {"name":"input.data","wave":"2345x.","data":["d3..d6","p5,d0..d2","p1..p4","0,0,0,p0"]},
  {"name":"input.last","wave":"0..10."},
  {"name":"output.valid","wave":"0...10"},
  {"name":"output.ready","wave":"1....."},
  {"name":"output block","wave":"x...2x","data":["msg + S"]}
],"head":{"text":"RsSyndromes: RS(13,7), U=4, buffered=false","tick":0},"config":{"hscale":3}}
....

When an output block is held, minimal mode accepts a new input beat only
when that result can transfer. Buffered mode can hold one next-frame beat
while the result waits; it cannot compute that beat until the result clears.
The optional holding register does not add an obligatory cycle when empty.

The accepted beat count must be exactly `C` when `last` arrives. Early or
late `last` discards the frame without an output transaction. The beat
counter saturates on an overlong frame; the stage continues accepting and
discarding until `last` allows it to start a fresh frame. There is no timeout
or separate malformed-frame status. Input gaps merely pause the calculation.
