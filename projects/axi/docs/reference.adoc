[[axi4-reference]]
== AXI4 reference

This chapter collects the details that the API chapters refer to: the
configuration type, the payload layout, the burst rules that requests must
satisfy, and the reset and pin conventions. Source paths in this chapter are
relative to `projects/axi/rtl/`.

[[axi4-configuration]]
=== Configuration

`axi_config(...)` returns a configuration type `C`. Pass the same type
throughout a connected hierarchy. `AxiDefault` is the default configuration.

[options="header",cols="2,1,3"]
|===
|Parameter |Default |Meaning and constraints
|`addr_width` |32 |Positive byte-address width.
|`data_width` |32 |Power of two from 8 through 1024 bits.
|`id_width` |4 |Nonnegative; zero selects the single implicit ID.
|`awuser_width`, `wuser_width`, `buser_width`, `aruser_width`, `ruser_width`
|0 |Independent nonnegative USER widths; zero omits the corresponding flat signal.
|`protocol` |`Protocol.Axi4`
|`Axi4`, `Axi3`, or `Lite` (AXI4-Lite). AXI4-Lite requires a 32- or 64-bit data
 width, `id_width` zero, and no USER signals.
|===

[[axi-protocols]]
==== AXI3 and AXI4-Lite

The protocol changes the payload types (see <<axi4-payloads>>) and a few rules.
The APIs and examples are written once: they read payload fields only through
the configuration's accessors, which resolve the protocol during elaboration:

[options="header",cols="2,3"]
|===
|Member |Meaning
|`C.protocol`, `C.axi3`, `C.lite` |The selected protocol.
|`C.max_beats` |Longest encodable burst: 256 (AXI4), 16 (AXI3), 1 (AXI4-Lite).
|`C.len_of`, `C.size_of`, `C.burst_of`, `C.cache_of` |Address attributes; AXI4-Lite
 requests read as single full-width INCR beats with no cache attributes.
|`C.exclusive(a)` |Exclusive access: AXI4 LOCK, AXI3 LOCK == 1, never for AXI4-Lite.
|`C.id_of(x)`, `C.with_id(a, id)` |ID of an address, response or AXI3 W payload; zero
 where the protocol has none.
|`C.last_of(x)`, `C.user_of(x)` |LAST of a W or R payload (always true for AXI4-Lite)
 and its USER field (zero where absent).
|`C.make_w`, `C.make_b`, `C.make_r` |Construct a payload; fields the protocol lacks are
 dropped, and an AXI3 W carries its burst's ID (WID).
|===

Rules that differ from AXI4:

* **AXI3:** AxLEN is 4 bits, so bursts have at most 16 beats; AxLOCK is 2 bits
  (0 normal, 1 exclusive, 2 locked, 3 reserved and rejected); there are no QoS
  or region fields. W carries WID. The Manager sets it to the burst's AWID and
  never interleaves write data. The Subordinate declares a write-interleaving
  depth of one, as AXI3 permits, and treats a WID that differs from the oldest
  open burst's AWID as a peer error.
* **AXI4-Lite:** every transaction is one full-width beat, with no ID, LAST,
  attributes other than PROT, or USER. Responses therefore return in issue
  order. The Subordinate keeps them in order through its ID-0 context matching,
  and the pooled Manager matches them the same way. The fixed-ID Manager
  (`manager()`) records the issuing endpoint of each AR and AW in issue-order
  queues and routes R and B from their heads (see <<axi4-manager-internals>>).
  Its endpoint IDs are then local labels that never appear on the bus.

`C.Addr`, `C.Data`, `C.Id`, and `C.Strobe` are unsigned hardware types.
`C.bytes` is the bus width in bytes, and `C.size` is the SIZE encoding of a
full-width beat. `C.fixed`, `C.incr`, and `C.wrap` are burst codes 0, 1, and 2.
`C.okay`, `C.exokay`, `C.slverr`, and `C.decerr` are response codes 0 through 3.

[[axi4-payloads]]
=== Payloads and the bus interface

Source: `axi/types.kh` and `axi/interfaces.kh`.

[options="header",cols="1,4"]
|===
|Payload |Fields in declaration order
|`C.Aw`, `C.Ar` |`id`, `addr`, `len`, `size`, `burst`, `lock`, `cache`, `prot`, `qos`, `region`, `user`
|`C.W` |`data`, `strb`, `last`, `user`
|`C.B` |`id`, `resp`, `user`
|`C.R` |`id`, `data`, `resp`, `last`, `user`
|AXI3 `C.Aw`, `C.Ar` |`id`, `addr`, `len` (4 bits), `size`, `burst`, `lock` (2 bits), `cache`, `prot`, `user`
|AXI3 `C.W` |`id`, `data`, `strb`, `last`, `user`
|AXI4-Lite `C.Aw`, `C.Ar` |`addr`, `prot`
|AXI4-Lite `C.W`, `C.B`, `C.R` |`data`, `strb`; `resp`; `data`, `resp`
|===

Encoded fields keep their AXI widths: LEN 8, SIZE 3, BURST 2, CACHE 4, PROT 3,
QOS 4, REGION 4, RESP 2, and LOCK/LAST 1 bit. Raw encoded fields stay
representable, so that monitors can diagnose illegal peers.

`read_request(C, addr, beats=1, ...)` and `write_request(...)` construct
address payloads with a beat count from 1 through `C.max_beats`, converting it to
`len=beats-1`. For AXI3, `lock=true` encodes an exclusive access as 1, and QoS
and region must stay zero. For AXI4-Lite, every argument other than `addr` and
`prot` must keep its default. Defaults select ID zero, a full-width INCR burst, no exclusive
access, and zero attributes and USER. Optional arguments correspond to the
address fields above. Submission validates the complete request: constructing
a raw payload does not make an illegal combination valid.

`Axi(C)` exposes the `aw`, `w`, `b`, `ar`, and `r` typed payloads, each with
its `valid` signal and reverse `ready` signal. Its `Manager` and `Subordinate`
views set all directions. KHDL interfaces cannot currently contain other
interfaces (https://github.com/khdl-lang/khdl/issues/40[khdl#40]), so `Axi(C)` is flat. `manager_channels` and
`subordinate_channels` in `axi/interfaces.kh` recover five generic channel
endpoints from it through `ChannelSignals(T)` reference bundles. These are
elaboration-time aliases, with no hardware pointers or extra buffering.

KHDL exports each payload as a packed signal. Declared struct fields pack from
the least significant bits upward. Byte lane zero is `data[7:0]`, controlled by
`strb[0]`. Multi-byte memory values use increasing byte addresses in increasing
lanes. There is no message padding convention: narrow and unaligned transfers
use the byte lanes selected by SIZE and the current address. WSTRB must be a
subset of those lanes, and zero strobes are legal. Read bytes outside the
selected lanes are unspecified by the API; `AxiRam` returns zero there.

[[axi4-bursts]]
=== Burst rules and feature coverage

`axi/burst.kh` provides `valid_request`, `beat_address`, and `lane_mask`, shared
by both endpoint roles. A Manager checks each request when the application
submits it. A Subordinate checks each request it receives, and each W beat's
WLAST and strobes. The legal requests are:

* SIZE no wider than the bus, and no address overflow.
* INCR bursts of 1 to 256 beats that stay within one 4 KiB page.
* FIXED bursts of 1 to 16 beats.
* WRAP bursts of 2, 4, 8, or 16 beats, with a start address aligned to SIZE.
* Exclusive (LOCK) requests with a power-of-two beat count up to 16, at most
  128 bytes in total, and an address aligned to that total size.
* AxCACHE allocate bits (bits 3 and 2) only together with the Modifiable bit
  (bit 1).

The following matrix identifies implementation and verification coverage. It
is not a claim of exhaustive AXI4 conformance testing.

[options="header",cols="2,3,3"]
|===
|Feature / specification topic |Implementation |Verification
|Independent channels, stalls; A3 handshake dependencies
|Registered Transmitter/Receiver; AW and W captured separately
|Random five-channel stalls and stability, W-before-AW, independent peers; bounded protocol monitor
|Reset; A3 reset requirements
|Async reset in AXI modules; all outgoing VALID cleared; coordinated cancellation
|Simulation reset checks; reset at any cycle in the bounded formal checks
|Burst address/length/lane rules; A3 transaction structure
|INCR 1..256, FIXED 1..16, WRAP 2/4/8/16; narrow and unaligned legal requests
|Independent arithmetic reference, raw burst tests, external AxiMaster/AxiRam
|Boundaries and malformed requests; A3 transaction structure
|SIZE no wider than bus, no address overflow, INCR stays within 4KiB;
WRAP beat-aligned and power-of-two span; request assertions before local issue
|Negative request cases, WLAST/WSTRB peer violations, page crossings; bounded protocol monitor
|IDs and ordering; A5 transaction identifiers
|Per-ID response association/order, different-ID interleaving, ordered W scheduling
|Adversarial reordered B/interleaved R, repeated IDs, non-power-of-two capacity; bounded protocol monitor
|Responses and error completion; A3 response signaling
|All four response codes represented; errors do not shorten bursts
|DECERR target/router, response-error injection and copy error handling
|Exclusive accesses; A7 exclusive accesses
|LOCK preserved, exclusive request restrictions checked; EXOKAY only for LOCK
|Nonmonitoring RAM exclusive transactions, invalid combinations
|Attributes and USER; A4 attributes and A8 additional signals
|All fields represented; pipeline/router preserve them; RAM ignores advisory attributes
|Bit-exact transport with distinct USER widths, zero-ID/zero-USER profiles
|===

`AxiRam` has no exclusive-access reservation monitor. It ignores LOCK, returns
OKAY for successful accesses, and performs writes normally. This is the
standard's behavior for a Subordinate without a monitor; OKAY does not report
exclusive success. A future backend can implement a monitor and use EXOKAY
through the same Subordinate API.

[[axi4-reset]]
=== Reset and external pins

The demonstration modules expose `clk` and an active-high asynchronous `rst`,
and use `clocked(clk, async rst)`. Their bus signals share that domain. Assert
reset asynchronously; the system must release it synchronously to `clk`. These
modules contain no reset-release synchronizer.

Reset cancels all outstanding contexts, clears outgoing VALID, and sets receive
READY to true. Input sampled during reset is dropped. Payload and memory values
reset to `undef` where unused. Connected endpoints must reset together:
recovery from a partial reset is unsupported.

The interoperability adapter `tools/axi_wrapper.py` exposes conventional flat
AXI pins and an active-low `aresetn`, inverted to the internal `rst`. Zero-width
ID and USER pins are omitted. This adapter is test-boundary wiring around the
normal KHDL export, not hardware code generation for the transaction API.
Integrations that use a different pin naming convention can apply the same
payload unpacking and reset inversion. The generic channel examples keep their
documented synchronous reset (<<axi-channel-endpoints>>), whose domain comes
from the caller.
